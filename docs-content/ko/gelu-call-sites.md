# GELU 호출 지점과 각 지점이 포팅하는 upstream activation

#2423의 인벤토리입니다. `mlxcel_core::gelu_approx`는 이름과 달리 정확한 erf GELU를 계산하는 반면, MLX의 `nn.gelu_approx`(및 `nn.GELU(approx="precise")`)는 tanh 근사입니다. 따라서 호출 지점의 이름만으로는 그 포트가 어떤 공식을 필요로 하는지 알 수 없습니다. 이 파일은 `src/` 아래의 모든 비테스트 호출 지점을 그것이 계산하는 공식과, 해당 지점의 mlx-lm / mlx-vlm / mlx-audio 참조 구현이 계산하는 공식에 매핑합니다.

범위: `gelu_approx`, `compiled_gelu_approx`, `gelu`(erf), sigmoid/fast 변형(`gelu_sigmoid`, `gegelu`), C++ `gelu_tanh_approx` 헬퍼와 그것을 쓰는 fused 코드, 그리고 모든 private Rust tanh/erf 복사본의 모든 비테스트 호출 지점. 테스트 전용 코드(`*_tests.rs`, `#[cfg(test)]` 모듈, `xla-diagnostics` 테스트 모듈)는 명시한 경우를 제외하고 제외합니다. 줄 번호는 #2423의 변경 이전인 `main` 4658ae83 기준이며, #2423이 변경한 행은 **changed in #2423**으로 표시했습니다.

upstream 소스는 설치된 사본에서 읽었고 모든 링크는 해당 리비전에 고정되어 있습니다. mlx 0.32.4, mlx-lm `c39139d70`(0.32.3.dev2), mlx-vlm v0.7.8, mlx-audio v0.5.9. Hugging Face activation은 transformers 5.20.1(`ACT2FN`, `*Config` 클래스 기본값, 라이브러리 내 `minicpmv4_6`, `gemma4`, `gemma3n`, `siglip` modeling 코드)과 체크포인트 자체의 `config.json` 및 remote code에서 읽었습니다.

"Upstream" 열에 사용한 MLX 의미([mlx/nn/layers/activations.py](https://github.com/ml-explore/mlx/blob/v0.32.4/python/mlx/nn/layers/activations.py)): `nn.gelu`, `nn.GELU()`, `nn.GELU(approx="none")` = **erf**. `nn.gelu_approx`, `nn.GELU(approx="precise")`, `nn.GELU(approx="tanh")` = **tanh**. `nn.gelu_fast_approx`, `nn.GELU(approx="fast")` = **fast**(`x * sigmoid(1.702 x)`). Hugging Face `ACT2FN`: `gelu` = erf, `gelu_pytorch_tanh` / `gelu_new` / `gelu_fast` = tanh, `quick_gelu` = fast.

공유 mlx-vlm MLP 클래스([mlx_vlm/models/mlp.py](https://github.com/Blaizzy/mlx-vlm/blob/v0.7.8/mlx_vlm/models/mlp.py)): `GELUMLP` = tanh(`approx="precise"`, :36), `FastGELUMLP` = fast(:50), `TanhGELUMLP` = tanh(:65).

판정(Verdict)은 mlxcel을 그것이 따르는 mlx-lm / mlx-vlm / mlx-audio 포트와 비교한 것입니다. upstream이 체크포인트 자체의 Hugging Face activation과 다른 경우 Notes 열에 그렇게 적었습니다. 그 경우의 MISMATCH는 mlxcel이 학습된 activation을 따르고 참조 구현은 그렇지 않다는 뜻이기 때문입니다.

## 0. #2423이 바꾼 것과 바꾸지 않기로 결정한 것

새 코드는 `mlxcel_core::utils::GeluActivation`(`Erf`, `Tanh`, `TanhF32`, `TanhF32Compiled`, `Fast`, 그리고 config 문자열용 `from_hf_name`)으로 공식을 선택하며, 이는 fused GeGLU 커널이 사용하는 C++ `gelu_tanh_approx` 헬퍼가 뒷받침합니다. `TanhF32Compiled`는 `TanhF32`를 하나의 컴파일된 커널로 만든 것이며(f32 반올림 범위에서 동일), #2423에서 전환된 패밀리는 전환이 prefill 시간을 늘리지 않도록 이것을 사용하고, `TanhF32`로 통합된 호출 지점은 eager이며 비트 단위로 정확한 헬퍼를 유지합니다. 각 결정의 근거가 된 측정은 [benchmark_results/gelu-erf-vs-tanh-2026-10-23.md](benchmark_results/gelu-erf-vs-tanh-2026-10-23.md)에 있습니다.

## 0b. #2423이 남겨 둔 패밀리에 대한 최종 결정 (#2548)

아래 모든 행에 적용한 결정 규칙:

1. 체크포인트가 결정합니다. 그 `config.json`(`hidden_act`, `hidden_activation`, `vision_config.hidden_act`, 또는 패밀리 자체의 키)과, 키가 없으면 해당 `model_type`에 대한 Hugging Face config 클래스의 기본값(Hugging Face는 클래스 기본값과 같은 키를 버립니다)을 `transformers.activations.ACT2FN`이 하는 방식으로 평가합니다. Remote-code 체크포인트는 자체 modeling 파일에서 읽습니다.
2. mlx-lm / mlx-vlm 포트와 교차 확인합니다. MLX 포트가 Hugging Face에서 벗어나는 경우 mlxcel은 Hugging Face를 따르고 해당 행에 그 차이를 기록합니다.
3. 각 행에는 한 줄짜리 근거가 있습니다.

logit-trace 게이트는 erf와 tanh를 구분하지 못하므로(0절 참고) 이는 config 결정이며, 로컬 체크포인트가 있는 패밀리마다 `mlxcel generate` 한 번과 `mlxcel-server` 요청 한 번으로 smoke 테스트했습니다(결과는 #2548 PR에 있음). 변형: "tanh (f32, compiled)"는 `GeluActivation::TanhF32Compiled`로 #2423이 전환된 패밀리에 선택한 것이고, "tanh (input dtype)"은 C++ `gelu_tanh_approx` 헬퍼(`GeluActivation::Tanh` 또는 fused Gemma GeGLU 커널)로 형제 Gemma 커널과 XLA bf16 tape가 이미 그렇게 계산하는 곳에서 사용합니다. "fast"는 `GeluActivation::Fast`(`quick_gelu`)입니다.

### 2d. 공유 SigLIP / CLIP encoder (`src/vision/encoders/siglip.rs`)

`siglip.rs:126-130`의 `VisionMLP::forward_impl`은 `VisionConfig.hidden_act`(`src/vision/config.rs:34-40`)에서 `select_mlp_activation`(`siglip.rs:63`)이 고른 `VisionMlpActivation`에 따라 dispatch합니다. `"gelu_pytorch_tanh"` -> `PytorchTanh`(`siglip.rs:92`의 private f32 tanh). **키가 없는 경우, `"gelu"`, `"quick_gelu"`를 포함한 그 밖의 모든 값 -> `Exact` -> `mlxcel_core::gelu_approx`(erf)**이며, 로더가 `use_fast_gelu = true`를 전달하는 경우(-> `gelu_sigmoid`, fast)는 예외입니다. HF는 `hidden_act`가 SiglipVisionConfig 기본값(`gelu_pytorch_tanh`)이나 CLIPVisionConfig 기본값(`quick_gelu`)과 같으면 이를 생략하므로, 기본값에 의존하는 config는 mlxcel에서 erf로 해석됩니다.

#2423 이후 Gemma 3 VLM과 PaliGemma 로더는 `VisionConfig::default_missing_hidden_act_to_siglip`으로 누락된 키를 `VisionHiddenActivation::SiglipDefaultTanh`로 해석하며, `select_mlp_activation`이 이를 `PytorchTanhCompiled`(컴파일된 f32 tanh, `GeluActivation::TanhF32Compiled`)로 매핑합니다. 선언된 `gelu_pytorch_tanh`는 여전히 `PytorchTanh`(eager `TanhF32`)로 매핑됩니다.
