# 모델 카탈로그

`docs/model-catalog.tsv`는 벤치마크 스토어 아래의 각 디렉터리가 실제로 무엇을 담고 있는지, 어느 머신에 있는지, 어떤 근거에 기반하는지를 기록합니다. 벤치마크 행은 이름으로 읽히므로 모델을 잘못 기술하는 이름은 측정을 잘못 기술하게 되며, 같은 체크포인트가 머신과 날짜에 따라 서로 다른 이름을 가져 왔기 때문에 이 문서가 존재합니다.

스토어는 `models/`이며 그 외에는 없지만, `models/`는 모든 머신에서 같은 형태가 아닙니다. M5 Max는 체크포인트를 그 바로 아래에 보관하고, M1 Ultra는 이를 심볼릭 링크로 만들어 그 아래에 두 개의 루트인 `models/mlx/`와 `models/mlx-big/`을 유지하며, 후자는 120 GB를 넘는 체크포인트용입니다. 두 가지 결과가 따르며 둘 다 이미 잘못된 문서를 낳았습니다. 모든 루트를 스캔하십시오. `models/mlx/`만 읽으면 실제로는 존재하는 체크포인트 아홉 개가 M1 Ultra에 없다고 보고되었고, 그중 여덟 개는 측정된 행이 이미 `benchmarks/` 아래에 커밋되어 있었습니다. 그리고 경로 리터럴이 아니라 basename으로 일치시키십시오. `ls -d models/<name>`으로 작성된 검사는 같은 체크포인트에 대해 한 호스트에서는 통과하고 다른 호스트에서는 실패하므로 스토어가 아니라 레이아웃을 테스트하는 것입니다. `~/.cache/mlxcel/models`는 범위 밖입니다. 그 내용은 머신마다 다르므로 거기서 조립한 표는 다른 호스트의 표와 나란히 읽을 수 없습니다. 해당 캐시로의 심볼릭 링크를 통해서만 접근 가능한 체크포인트는 스토어에 있는 것이 아니므로, 실제 디렉터리를 옮겨 오십시오. `mlxcel list`는 스토어가 아니라 그 캐시를 보고하므로, 스토어에 체크포인트가 이백 개 있어도 "No models downloaded"를 출력하거나 완전해 보이지만 그렇지 않은 짧은 목록을 출력할 수 있다는 점에 유의하십시오.

## 명명 규칙

디렉터리 이름은 체크포인트가 무엇인지, 즉 패밀리, 크기, 튜닝, 정밀도를 말해야 합니다. 네 단계가 순서대로 이를 결정합니다.

1. **README 제목을 읽습니다.** mlx-community 변환본에는 quantization을 포함하여 아티팩트 자체를 지칭하는 `# mlx-community/<repo>` 줄이 있습니다. 존재하면 이것이 권위입니다.
2. **`base_model:`로의 폴백은 답이 아니라 경고로만 사용합니다.** 해당 frontmatter 필드는 아티팩트가 *변환된 원본* 체크포인트를 지칭하므로, 이를 따르면 4-bit 변환본이 bf16 원본의 이름을 따르게 됩니다. 변환이 아니라 원저자가 직접 게시한 체크포인트에는 제목이 없으며, 폴백이 작동한다는 사실 자체가 결과 이름이 다른 무언가를 기술할 수 있다는 신호입니다.
3. **업스트림 이름에 없는 정밀도 토큰은 유지합니다.** `mlx-community/Llama-3.1-8B-Instruct`는 정밀도가 없지만 로컬 디렉터리에는 있었고 4-bit 형제 옆에 놓여 있습니다. 접미사를 떼면 이 쌍이 bf16 대 양자화가 아니라 base 대 양자화로 읽힙니다. 사라진 토큰은 복원하되, 원래 없던 것을 만들어 내지는 마십시오.
4. **이름을 config와 대조하고 config를 믿으십시오.** `hunyuan-1.8b-4bit`의 README는 `Hunyuan-4B-Instruct-1.8bit`를 가리키지만, 체크포인트는 `bits: 4`에서 1.85B 파라미터로 측정됩니다. 디렉터리 이름이 옳고 README는 복사 오류이므로 이름은 유지됩니다.

제목도 `base_model`도 없으면 이름을 그대로 두십시오. config로 조립한 이름은 추측인데도 검증된 것처럼 읽히며, `id_source: none`이 이를 대신 분명하게 말해 줍니다.

## 컬럼

| 컬럼 | 의미 |
|---|---|
| `local_name` | `models/` 아래의 디렉터리 이름. |
| `aliases` | 이름이 바뀌기 전에 이 체크포인트가 측정된 이름들로, `;`로 구분됩니다. 과거 날짜의 CSV 행은 이를 통해 현재 행에 조인됩니다. 별칭은 하나의 가중치 집합이 다른 이름을 가졌었다는 것을 기록하는 것이지, 디렉터리가 한때 다른 모델의 이름으로 잘못 명명되었다는 것을 기록하는 것이 아닙니다. `jamba-v0.1-4bit`는 AI21-Jamba-Reasoning-3B를 담고 있었고 Jamba v0.1은 스토어에 있었던 적이 없으므로, 그 디렉터리의 이름을 바꾼 것은 옳았으나 옛 이름을 별칭으로 나열한 것은 옳지 않았습니다. |
| `upstream_repo_id` | HuggingFace repo이며, 어느 출처에서도 얻지 못하면 비어 있습니다. |
| `id_source` | `heading`, `base_model`, `none`. 신뢰도는 이 컬럼만으로 읽을 수 있습니다. |
| `precision` | `config.json`에서, 또는 `torch_dtype`이 없으면 shard 헤더에서 가져옵니다. |
| `size_gb` | 디스크 상의 점유량으로, 머신 간 전송을 계획할 때 기준이 되어야 하는 값입니다. |
| `present_on_m1ultra`, `present_on_m5max` | 각 호스트가 자신의 컬럼을 소유합니다. |
| `verified_by` | 업스트림 id를 config와 교차 확인했으면 `config`, 아니면 `none`. |
| `store` | 표준 스토어는 `repo`. |
| `shards_ok_m1ultra`, `shards_ok_m5max` | 호스트별 shard 판정으로, `ok(N)` 또는 결함. |
| `csv_rows`, `doc_mentions` | 이름과 그 별칭이 가진 벤치마크 행과 문서 참조의 수. 이름을 바꾸기 전에 그 비용을 가늠하게 해 줍니다. 비용은 균일하지 않으며 가장 큰 항목은 백 개가 넘는 행에 걸쳐 있습니다. |
| `m5_absence` | 한 호스트에 있는 체크포인트가 다른 호스트에 없는 이유로, 그 부재가 결함이 아니라 결정일 때 기록합니다. |

## Shard 무결성

`shards_ok_*`는 각 shard의 선언된 길이 `8 + header_len + max(data_offsets[1])`를 파일 크기와 비교합니다. 가중치를 읽지 않고도 잘린 다운로드와 손상된 헤더를 잡아냅니다.

디렉터리의 존재만으로는 충분하지 않으며, 이것이 이 컬럼이 존재하는 이유입니다. 두 항목은 한때 config와 README만 있고 `.safetensors`는 전혀 없었으며, 수십 기가바이트가 `.cache/` blob 안에 구체화되지 않은 채로 있었습니다. 둘 다 이름은 올바랐고, 둘 다 다른 호스트로의 전송 목록에 올라 있었으며, 유일한 신호는 모든 측정 컬럼이 비어 있는 벤치마크 행이었습니다.

## 재생성

`models/*/`를 순회하며 README 제목을 읽은 뒤 `base_model` 줄을 읽고, 정밀도와 quantization을 위해 `config.json`을 읽고, shard 검사를 실행하고, `benchmarks/*.csv`와 `docs/` 전반에서 이름과 별칭의 출현 횟수를 셉니다. 문서 언급은 끝 경계(`(?![A-Za-z0-9._-])`)를 두고 세십시오. 그렇지 않으면 짧은 이름이 그것으로 시작하는 모든 더 긴 이름을 흡수합니다.

각 호스트는 자신의 존재 여부 및 shard 컬럼을 채우고 다른 호스트의 컬럼은 그대로 두므로, 둘은 어느 쪽도 자신이 관찰할 수 없는 것을 덮어쓰지 않고 병합될 수 있습니다.
